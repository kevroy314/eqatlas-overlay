Versions & feedback

Knowing when there is an update, getting back off a bad one, and telling me when something is broken — none of which needs a server.

The bottom of the Trail panel carries a small row:

v0.7.0 · update to 0.8.0 →
[issue] [idea] [versions] [updates]

Knowing about updates

The version line says which build you are running. When a newer one exists it becomes a link straight to the install page, and Tampermonkey takes it from there.

This is the only network request EQ Trail ever makes: a plain fetch of one static JSON file from the project's own GitHub Pages, cached for a day, carrying no parameters and no information about you. If it fails — offline, a firewall, a page policy — it fails silently and the overlay carries on.

Turn it off with the updates button and the overlay is entirely offline again, which is how it behaved for its first six versions. The version number still shows; it just stops looking for newer ones.

Going back a version

versions lists recent releases. Each is a pinned build — it deliberately carries no update URL, so once installed it stays where it is. Without that, Tampermonkey would spot the newer release at the other end and quietly pull you straight back to the version you were escaping.

Click one and Tampermonkey offers to install it, replacing what you have. Nothing else to do.

Coming back. Versions before 0.7.0 have no version row, so once you roll back that far the button to return is not there. Use the install page — it always points at the current release.

Reporting a problem or asking for something

issue and idea open a GitHub issue form, pre-filled: a short prompt for what happened, plus a collapsed block of diagnostics. Nothing is sent until you press submit on GitHub, and you can edit or delete any of it first.

What the diagnostics contain

IncludedNever included
EQ Trail version and how it was installed
Browser and graphics card
Which zone is loaded, and the three.js version
Counts — locs, zones, runs, gravestones, heat cells, gaps
Your current settings		 Your log file, or any part of it
The file name — which carries your character name
Any coordinate you visited
Any timestamp from your session

The counts are there because they are what makes a report actionable — "26 locs across 8 zones, 3 runs, no gravestones" says more about a rendering bug than a paragraph of description usually does. If you would rather not send even that, delete the block before submitting.

Please do not paste log contents into an issue. A description of what you were doing is more useful and does not put your character's movements on the public internet. If a specific log really is needed to reproduce something, say so in the issue and we can work out a way.
